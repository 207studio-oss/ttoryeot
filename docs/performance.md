# 성능 기준선

## 요약

저장소 안의 합성 HWPX 한 문서를 릴리스 채점기로 100번 채점해 잰 값입니다. 2026-10-27에
Windows PC에서 직접 돌렸습니다.

| 항목 | 값 |
|---|---:|
| 문서 | `hwp-core/tests/fixtures/synthetic.hwpx` (합성, 저장소 안) |
| 쪽/회 (평균) | 11 |
| 측정 횟수 | 100회 (예열 5회 제외) |
| 전체 쪽 | 1,100 |
| 전체 시간 | 1.195초 |
| **쪽/초** | **920.22** |
| 회차별 쪽/초 중앙값 | 925.32 |
| **최대 작업 집합** | **15,704,064바이트 (14.98MiB)** |

- 이전에 기록한 성능 기준선은 없습니다. 이 표가 첫 값입니다.
- 100회 측정을 3번 반복했습니다. 세 실행의 쪽/초는 903.25–921.49였고, 표는 가운데
  실행(920.22쪽/초)입니다.
- 비공개 말뭉치는 읽지 않습니다. 저장소 안의 합성 문서와 `assets/fonts`만 씁니다.
- 같은 PC·같은 문서·같은 릴리스 빌드에서만 비교하세요. 값은 출시 품질 보증이 아닙니다.

## 무엇을 쟀나

`ttoryeot-score bench`는 한 회차마다 다음을 차례로 합니다.

1. `hwp-core`로 문서를 파싱합니다.
2. `ttoryeot`로 쪽에 배치하고 장면을 만듭니다.
3. `krilla`로 PDF를 메모리에 씁니다.
4. `hayro`로 그 PDF를 72dpi로 래스터화하고 글자를 뽑습니다.

이 경로는 말뭉치 채점에서 문서마다 도는 후보 생성·래스터화 작업과 같습니다. 글꼴 색인은
측정 전에 한 번만 하고 시간에 넣지 않습니다(채점기도 말뭉치 전체에서 한 번 색인합니다).
기준 PDF 읽기와 화소·글자 비교는 넣지 않았습니다. 기준 PDF가 저장소에 없기 때문입니다.

`쪽/초`는 `전체 쪽 ÷ 전체 시간`이고, 회차별 중앙값은 회차마다 그 회차의 쪽 수를 그 회차
시간으로 나눈 값의 중앙값입니다. `쪽/회`는 전체 쪽을 회차 수로 나눈 평균이라 소수점이 붙을
수 있습니다. 회차마다 쪽 수가 달라도 전체·회차별 값이 서로 맞습니다.

전체 시간은 소수점 여섯 자리까지 반올림해 찍고, 쪽/초·중앙값은 반올림 전 시간으로 계산해
소수점 2자리로 찍습니다. 위 표의 1.195초는 당시 소수점 3자리 표시라 1,100÷1.195≈920.50과
920.22가 조금 다릅니다. 표의 쪽/초는 반올림 전 시간으로 계산한 값입니다.

최대 작업 집합은 프로세스가 시작한 뒤 지금까지 도달한 최고 실제 메모리(Windows
`PeakWorkingSetSize`, Unix `ru_maxrss`)입니다. 글꼴 색인, 예열, 첫 렌더의 글꼴 로딩이 모두
포함되며 타이밍 구간만의 값이 아닙니다. `--warmup 0`은 글꼴을 처음 읽는 콜드 스타트 측정이라
예열을 넣은 값과 직접 비교하지 마세요. PDF는 디스크에 쓰지 않고 메모리에서 바로 래스터화합니다.

## 재현

Windows PowerShell에서:

```powershell
pwsh -File tools\bench.ps1
```

같은 일을 직접 하려면:

```powershell
cargo run --release --locked -p ttoryeot-score -- bench `
  --document hwp-core\tests\fixtures\synthetic.hwpx `
  --fonts assets\fonts --runs 100 --warmup 5
```

`--runs`는 측정 횟수, `--warmup`은 버리는 예열 횟수입니다. 결과는 JSON 한 벌로 찍힙니다.
`--document`는 현재 작업 트리 안의 파일이어야 하고, JSON에는 작업 트리 기준 상대 경로만
찍힙니다. 저장소 밖 문서는 이름도 찍지 않고 거부합니다.
